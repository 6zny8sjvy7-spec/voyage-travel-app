## 已批准的介面與互動（未達者仍為阻擋交付項）
1. **首頁目的地＋天氣**：合併為不互相遮蓋的視覺區域。保留原本會輕微跳動的國家／城市代表性建築與圖示（使用者同意保留），不得用其他 SVG 直接取代或壓到天氣卡。韓、泰、日、越各國切換有對應地標；天氣隨實際來源顯示晴／雨／雪／夜，未取得不得偽裝真實天氣；日夜模式明顯不同但仍高質感、文字易讀。
2. **單日／週行事曆**：單日時間軸與週行事曆均呈現時間順序且保留比例、當天選取與視覺效果；旅遊天數可自行增加、不可強迫固定三天，不能誤刪既有日程。點一下景點／餐飲／活動定位至**當頁下方既有地圖**；點兩下開編輯；不要每張卡片再放重複的「編輯」按鈕。點擊在觸控裝置應有可理解且安全的操作方式，不應造成單點與雙點衝突。
3. **地圖與底部費用頁籤**：使用者在上一個旅行 APP 對話已明確同意：底部導覽固定為「首頁／行程／交通／**費用**／更多」，原本「地圖」頁籤直接換成「費用」。費用頁直接開啟真正可記帳、查看預算、分帳及幣別／匯率換算的內容，不是空白按鈕；回到頁面／重新整理時旅行紀錄不得消失。單日及週行事曆下方已有內嵌地圖，所以不再出現獨立地圖分頁、也不需要首頁的重複「旅行地圖」捷徑；使用者可選 Google Maps／NAVER Map 外部導航，韓國地址使用可查詢的韓文或正確名稱；只顯示有來源的路線／座標，不得用直線冒充導航。此要求在 2026-11-13 上一個對話**已確認但當時尚未寫入程式**，不能把更早的程式發布狀態冒充最後要求。
4. **新增活動**：保留**單一**「＋安排活動（展開／收合）」入口，刪掉上方重複的「＋景點／＋餐飲／＋交通／＋購物」捷徑列；預設盡量收合，不讓整頁被新增表單佔據。內容依類別顯示真正必要欄位；依交通種類切換「步行／地鐵或 BTS／計程車或 Uber／公車／航班」對應欄位，不可只讓使用者手填時間與方向。
5. **航班／住宿**：在新增行程選到航班就能填**出發國家／機場、出發日期與當地時間、抵達國家／機場、抵達日期與當地時間、航班號**，保存後連動正確旅行日期；航班／住宿管理頁與日程須一致、不能有兩套互不相通欄位。當日期錯誤時要準確指出哪個日期、提供合理預設與明確修正方式；不得只說「時間不正確」。
6. **交通 A→B 查詢**：重點是精確的起終點、乘坐哪條線、**往哪個終點站／方向**、每段**搭幾站**與**中間所有站名**、正確轉乘。若 API 可可信取得 A 站相同路線、相同方向的下一班，才顯示幾分鐘進站（區分時刻表與即時），沒有則明確告知不支援。取消追蹤使用者上車、所在車站、下一站與列車背景 GPS；App 的手動目前位置地圖定位可以獨立保留。不可以把只有起終站的資料誤判 1 站，也不能把模擬 API 經過測試當成實際可用。
7. **行李**：備品可分類查找；個人勾選已打包時加刪除線但物品仍存在；單獨刪除模式不能與打包勾選混淆，資料跨重開保留。
8. **翻譯、幣別**：語言隨韓／泰／日／越切換，保留實用例句與翻譯工具；貨幣在旅行設定、開銷、換算選單用「國家／地區・貨幣名稱（ISO 代碼）」顯示，舊 ISO 資料鍵不變。
9. **AI 景點推薦**：使用者已正式要求移除，不得以別的名稱重新加入或保留佔位功能。不要擅自刪掉其他已批准功能。
10. **旅行資料**：切換國家／旅行前後資料保存，跨多趟旅行可回顧先前行程，保留匯出備份；若雲端同步無實際服務／帳號設定則標示未提供，不可宣稱已同步。

- 實際操作新增並修改出發與抵達跨時區航班，同時驗證無效日期的準確提示及行程保存。
- 用真實公開資料測試韓／泰／日／越不同路線（至少各國指定案例）；地鐵站名／方向／站數與官方圖核對，有資料來源與時間；遇到來源無結果時不偽造。
- 行程單擊定位、雙擊編輯，分別測單日和週行事曆。
- 在桌面及模擬 iPhone WebKit 測試版面／無橫向溢出，最後使用實體 iPhone Safari 驗收。
- 未執行／未通過的測試寫明，**不准**用「78 項通過」取代以上需求驗收。

## 2026-11-13 交通助手跨國一次性整改：不可分國家回頭翻修

此段是使用者最新明確批准的產品規格，不表示程式已完成。保護原 V2 旅行資料、頁籤、地圖、費用、行李、航班和其他功能，不得用舊 V1 覆蓋原 V2，也不得新開網址。**不允許外連網站作為交通路線查詢的兜底結果**，任何可展示資訊都必須留在 VOYAGE 畫面內。API 可從網路取資料，但不得把使用者導出到其他網站看方向和站數。

### 一次整改範圍
- 同時納入韓國、泰國、日本、越南；各國的地鐵、城市鐵路（包含韓國 AREX、泰國 BTS / MRT / Airport Rail Link）、公車，以及所在地可取得的同類公共運輸；不能韓國先做一套、換泰國再重做主邏輯。範圍以**實際城市和營運商**記錄覆蓋，不可籠統宣稱「全國都已支援」。
- 一組 A（出發站）→ B（抵達站）的查詢介面，輸入中文、英文及當地站名均須能查到候選站，使用者可確認同名站。
- 返回正確的路線／車號、登車站、下車站、方向（以營運商的終點站、headsign 或已驗證路段序列）、分段和合計搭乘站數、列車／公車按**該班次實際停靠順序**列出的中間站與轉乘站。步行不算站；不可把「只有 A、B 端點」當作一站。遇到快車、區間車、分岔路線和不同停靠模式，需以該班次的 stop_sequence 辨識。
- **站數是阻擋性驗收項**：在資料已覆蓋的 A→B 路線，必須顯示可核驗的正確站數。路線站序缺失時誠實回報「本路線停靠站資料不足，無法核實站數」，不得編造、不得以外部導航取代。若四國指定驗收路線有一條缺乏可核實站序，本輪不得聲稱「四國一次整改完成」。
- 到站分鐘：能取得與出發月台、路線、**正確行車方向**及實際班次相符、帶有資料更新時間的官方／授權即時資料，才顯示「即時預計 X 分鐘」；如只有可信時刻表可顯示「表定 HH:MM」，但不能標成即時倒數；沒有資料顯示「目前沒有可驗證的下一班資料」。
- **取消**「已上車」、「下一站」、「GPS 自動追蹤我搭到哪站」及一切假倒數；手動查看自己的位置僅為地圖功能，不等於即時車輛追蹤。
- 「不能導外網」特別適用查詢本身：不把查詢失敗時的按鈕改成 Google Maps / NAVER / 營運商官網連結。來源歸屬可顯示為純文字；查不到就提供 VOYAGE 內可操作的重試／更換候選站，不偽裝成功。

### 不重做全站的工程架構
1. 統一站點標準化層（國家、城市、營運商、路線 ID、方向、stop_id、站名語言別名、候選站），避免中文站名匹配失敗即報不存在。
2. 統一路線規劃核心（station sequence → leg → transfer → total stops），獨立於畫面與國家；對營運商版本、服務日期、各班停靠差異有辨識。
3. 各地資料 adapter 只輸出同一格式，優先官方資料／授權 GTFS、GTFS-RT／營運商 API；統一保存來源、版本日期、覆蓋區域與資料品質。
4. 若官方 API 需 key，金鑰不能硬寫在 GitHub Pages HTML / JavaScript；須透過安全的受控後端或 serverless 代理，並核對授權、配額、維護成本。沒有金鑰時不能宣稱相應即時服務已上線。
5. 真實資料整合先做**四國各選城市的地鐵／城市鐵路與公車實例**、站序及方向驗證，不能把 mock API 綠燈當成果。每種模式需含直達、轉乘、同名站／別名、反方向、快慢車／支線、時間表過期、服務無資料、離線資料等測試。
6. 將交通相關程式、資料、UI 和測試分模組版本化，鎖定資料 schema 與舊旅行的 localStorage 鍵，先跑全部 V2 回歸測試及手機 Safari 視覺核對；禁止整包重寫 index.html 或刪掉已批准功能。
7. 發布門檻：四國跨模式**真實 A→B 路線和站數**有案例與來源支持 + 既有其他模組回歸不倒退 + 公開固定測試網址實測；未達者標示「尚未驗收」，不能宣稱完成。
